## What is SIMD

As a programmer working in the field of high frequency trading. Latency is often one of the most important and impactful metric of the trading system. While the trading servers are pretty beefy with ample number of CPU core. We often tend to avoid multi-threading operations in the critical path to minimize the context switching/resource contentions etc. Instead, we try to squeeze every laste juice in a single CPU core. SIMD is an unavoidable topic in this space. As the name suggests, there are sort of "parallelism" in SIMD. However, the parallelism is limited to the "data" level. It is a little hard to explain the "data" level parallellism, but we can first take a look at the opposite: instruction-level parallelism. As the name suggests. It naturally involves simultaneous executions of instructions, which unavoidably involves multiple physical CPU cores. In SIMD, only a single CPU core is used. So where does the parallelism come from ? Well it comes from the modern CPUs' natural capabilities of dealing with more "bytes" simultaneously in each cycle. 

In a very simple example, you want to add 4 integers. You normally think of 4 CPU cycles: 1: add the first number to original number (0 here) and store it in some register; 2: add the second number to what's in the register; 3: add the third number to what's in the register; 4: add the last number to what's in the register. Now you are end up with 4 cycles. But modern CPUs often comes with "wide registers" They can actually do it this way: 1: load that 4 numebrs all together into one wide register. 2: reduce (sum) the four integers within it. Just like that. 2x reduction in instruction counts. It's just like magic. But no, it's just one of the modern CPUs' hardware features.


## The Standardization

As mentioned above. The SIMD functionality is tied to the CPU hardware. So why is C++26 relevant in this context ? Well, it's because C++26 standardizes the simd and provides a standard way of explicitly leveraging the SIMD capability of CPU. Before C++26. There have been several non-standard way of doing this:

- Rely on the compiler's auto-vectorization
- Use intrinsics
- Third-party libraries

For option 1: It's not a guarantee. And it's non-portable. You need to curate your compiler flags and investigate the disassembly to be sure the intended auto vectorization is actually generated. And to maintain this, you need to validate pretty often after you've updated any code in the hot path. When it's in a big code base. It's almost non-maintainable.

For option 2: It's the very basic way of explicitly using intrinsics. On intel x86 platforms, you'll need `#include <immintrin.h>`. And you are going to need to invoke all the double-underscore types and single-underscore functions. It really clutters the eyes.

For option 3: It's degined to address the problems of the first 2 approaches. There are many choices, `Highway`, `Vc`, etc, you name it. These thirdparty libraries provide just good enough abstractions to make it easy enough to use simd operations in an elegant enough way. These libraries are good enough more often than not. But as mentioned, they are not standardized. If you happen to disagree with your colleagues on your favourite libraries, there can be frictions caused becuase of this mismatch.

Entering C++26, as simd now already enters the standard. I think it would be a great way that we can start using the SIMD capabilities of our CPUs.

## New Headers, Namespace and Types

As the time of writing. It seems like only `GCC > 16.1.0` now supports C++26 SIMD. When you compile your program. C++26 needs to be used: `-std=c++26`.

The new simd facility comes within the `<simd>` header. You are going to need to include this header if you want to use any functionality of the new SIMD facility of C++26.

All the `std::simd` facilities are in the `std::simd` namespace, including the types and functions.

The very basic new type introduced in the new stadard is `std::simd::basic_vec` with the following signature:

```cpp
template< class T, class Abi = /*native-abi*/<T> >
class basic_vec;
```

The `T` is the so-called "vectorizable type". There is nothing too mythical about it. It's specified in a white-list form in the stadard. in a word, it's one of the followings:

- all integer types
- most of the floating-point types
- `std::complex<S>`, where `S` belongs to type 2.

The type `Abi` is just a tag type. Here are some of the most common ones:

- `std::simd::deduce_abi_t<T, N>`. Where `N` maens: How many values of type `T` you want to squeeze into this `simd_vec` type. A normal SIMD register has bit width starting from 128 bits and tops at 512 bits, depending on your specific hardware. If you've specified a type wider than what your system supports. It leads to a compile-time error. As the full name of this is very verbose, the `std::simd::vec<T, N>` alias is introduced to make it more concise. As you can tell from it's concise name. It's the centric data structure of the whole `std::simd` library. Kind of like that `std::string` is just an alias of `std::basic_string`.

- `std::simd::native_abi<T>`. This means the 'native' simd register of your platform. For example, if your platform has the 256 bit register ready for you as the native, and `T` is `std::int32_t`. Then you will have a simd vector with 8 32 bit integers side-by-side for you to use. Note: As you can see in the signature of the type `std::simd::basic_vec`. This type is the default type of the `Abi` tag. So you can simply do: `std::simd::basic_vec<T>` and it will default to a native abi. In older online tutorials, you may often see the type `std::simd::native_vec<T>`. This has been removed in the finalized C++26 standard.

- `std::simd::fixed_size<N>`. Where teh `fixed_size` is the number of bytes you intentend to create fro your simd type.
